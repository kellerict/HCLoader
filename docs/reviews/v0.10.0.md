## Verdict: **ÄNDERUNGEN NÖTIG**

No Blocker. There are two Majors:

- **M1:** "Delete new file" never checks that the original is still there. The dialog promises "The original
  stays".
- **M2:** The windows are spread in proportion to each file's own duration. A re-upload that is more than about
  2 minutes longer or shorter is never marked, even when the head matches 100 %.

Mixcloud/hearthis.at follow the platform rules: their own throttle and backoff, every request goes through yt-dlp
behind `before_request`/`_PagedGate`, and `yt_dlp` is still imported only in `ytclient.py`. The decode path is
safe (argument list, no shell, timeout, cancel, `CREATE_NO_WINDOW | BELOW_NORMAL`).

## Checked and in order

- **Module boundaries:** `yt_dlp` is imported only in `app/core/ytclient.py` (grep over `app/`).
  `core/fingerprint.py` and `core/platforms.py` contain no UI code and make no network calls. The new
  `api.py` methods mostly delegate (see m5).
- **Throttle per platform:** `config.platform_throttle_settings` is the one source for `api.py`, `headless.py`
  and `main.py --smoke`, and `Throttle.platform()` keys its state as `mixcloud.*` / `hearthis.*`, so backoff and
  counters are independent per platform. `_metadata_call` → `th.check_backoff()` + `before_request`. Paged
  listings go through `_PagedGate.urlopen` (pace + `backfill_request` per HTTP request).
  `sleep_interval_requests` comes from the platform section. `extractor_retries` is 0 for every non-YouTube
  platform (`ytclient.py:575`), `retries`/`fragment_retries` are 0, and a 403 is never retried
  (`_download_with_retry`). Cookies are YouTube only.
- **Listing paging:** the hearthis.at search, user and set listings are lazy generators that stop on a short page
  (`len(items) < HT_PAGE`). The Mixcloud user/playlist subclasses set `first:` to the head window and set
  `hasNextPage=False` once the window is full (`_McMixin._call_api`). The Mixcloud search sets
  `limit=min(50, n)`, and `SearchInfoExtractor` slices to n. Every endless-page case is bounded by
  `playlistend`/`limit`/`n`, except the case in m1.
- **Ids / archive keys:** prefixes are `mc:`/`ht:` (DB) and `mc-`/`ht-` (file names, Windows-safe). The archive
  lines `mixcloud <user>_<slug>` and `hearthisat <id>` match yt-dlp 2026.10.26 (`MixcloudIE` builds the id from
  the unquoted URL user + slug, and the ie_key is lower-cased). `_track_url` downloads Mixcloud only if the stored
  track page gives the same id, and `track_page_ok` limits hearthis/Mixcloud downloads to single track pages on
  the right host. The template still requires `{id}`, so the original and the re-upload can never share one file.
- **Download format:** Mixcloud uses `bestaudio/best`. hearthis.at uses `SC_FORMAT`, which excludes
  wav/aiff/flac originals. `keep_original_mixcloud/hearthis` skip the MP3 re-encode. All of them are in the
  settings and the GUI.
- **Fingerprint decode:** `build_command` is a list (no shell) with `-nostdin -threads 1`, `-ss` before `-i`,
  `-t` bounded, `-map 0:a:0`, mono 5512 Hz s16le. Memory is at most 10 min × 5512 × 2 B ≈ 6.6 MB of PCM for one
  window, and a 2-hour set is never decoded in full. A watcher thread kills ffmpeg on cancel or after 10 min.
  Exit codes are mapped to permanent/transient errors, and only permanent errors are stored (no retry loop).
  Unix gets `setpriority(10)` and Windows gets `BELOW_NORMAL_PRIORITY_CLASS`. One file at a time, and the queue
  waits while the loudness analysis decodes.
- **Algorithm:** the landmark pairs, the ±1-bin offset histogram, the score against the smaller print and the
  "≥ 2 segments" rule hold up. Simulated: a 60 s longer intro still matches (score 0.49, 2 segments), and the
  same intro followed by a different set does not (test). The pure-Python FFT costs ~0.34 ms per frame, and one
  fingerprint at the defaults (3 min + 3×30 s) takes ~3 s CPU, 5.5k hashes and a 44 KB blob. The index keeps
  ~750 distinct hashes per item. Candidates come from one `IN` query per 500 hashes, with
  `MAX_HASH_FANIN`/`MAX_CANDIDATES` caps, so the speed is fine.
- **Re-upload actions:** `delete_new` only works on the marked (newer) id (`fingerprint.info_of` guard) and goes
  through `library.delete_item`, which runs inside the target folder and under `FS_LOCK`. It removes the `.cue`
  first, keeps the archive line (never downloaded again), sets the row to `ignored`, then runs
  `fingerprint.forget` (index, print, marks on both sides). The original is never touched (but see M1).
  `keep`/`link`/`open` survive a re-scan (`mark()` keeps a decision for the same pair).
- **Backfill pass / queue:** the pass runs oldest download first, so the newer item gets the mark. It can be
  cancelled between items and inside ffmpeg (`_AnyEvent`), and new downloads are served between files. A start
  backlog (`since_pending`) covers items downloaded by the headless run. Errors per item do not stop the pass.
- **Migration 16:** adds tables only (fingerprints, fingerprint_index with both indexes, reuploads with a CHECK
  on state). It has an upgrade test from v15.
- **UI/XSS:** every new string that comes from data goes through `esc()` or `textContent`. `ui.menu` escapes
  `head`/`label`, and `ui.toast` escapes. The thumbnail allowlist was extended exactly
  (`thumbnailer.mixcloud.com`, `*.hearthis.at`, https only, no userinfo/port).
- **Privacy docs:** the installer privacy text (EN/DE) and `docs/wiki/Code-Signing-Policy.md` list the new hosts
  and the on/off switches. The fingerprint is offline only.
- **Configurability:** `mixcloud.*`, `hearthis.*`, `reupload.*` and `download.keep_original_*` are all in the
  models, `config.example.yaml`, COMMENTS and the settings view (tabs `sources`/`reupload`).
  `_normalize` covers both new throttle sections.

## Findings (by severity)

### M1 – "Delete new file" can delete the last copy (Major)

`app/api.py:2351-2360` (`resolve_reupload`, `delete_new`) only checks that a mark exists.
`ui/js/views/library.js:541` enables the menu item regardless of `r.of.in_library`, and the dialog text says
"The original stays."

Scenario: the original file was moved or deleted in Explorer (the library shows it as "missing", status still
`done`), or the original row was re-queued or failed. The user trusts the dialog and deletes the newer file. No
copy is left, and the deleted item is now `ignored`. Its archive line also stays, so the watchlist will never
fetch it again.

Proposal: in `resolve_reupload` (or better in a core helper), refuse `delete_new` unless the `of` row has status
`done` and its `file_path` exists (`Path.is_file()` under the target root). Return a translated error
(`reupload.original_missing`). In the UI, disable `ru-del` when `!r.of.in_library`, and add a test.

### M2 – Re-uploads that differ in length by more than ~2 min are never detected (Major)

`app/core/fingerprint.py:203-217` (`windows_for`) places the extra windows at `head + rest·i/(w+1)`, which
depends on the duration of each file. `is_match` (`:267-271`) needs hits in at least 2 segments. If the two
files differ in length by Δ, window i moves by Δ·i/(w+1) relative to the other file's content (tail difference),
or by d·(1−i/(w+1)) (intro difference). After 30 s no window overlaps, so only the head hits.

Simulated with `tests/test_fingerprint.py:render` (1 h set, defaults 3 min + 3 windows):

| case | segments_hit | score | is_match |
|---|---|---|---|
| intro +60 s | 2 | 0.49 | True |
| intro +150 s | 1 | 0.11 | False |
| same audio, +150 s at the end | 1 | **1.00** | **False** |
| same audio, +10 min at the end | 1 | **1.00** | **False** |

A festival set re-uploaded without the crowd outro or aftermovie, or the Mixcloud radio show compared with the
YouTube cut, is exactly this case. `docs/wiki/Re-upload-Detection.md:18` is also wrong ("a longer or shorter
intro only shifts all of them by the same amount" – not the windows). `:63` mentions only the intro and
recommends "fewer windows". With `windows=0`, the protection against "same intro, different set" goes away.

Proposal (bump `VERSION`, so the prints are recomputed automatically):

- Anchor half of the windows to the start (absolute times, e.g. head + k·N min). These survive a different ending.
- Anchor the other half to the end (duration − k·N min). These survive a different intro.
- Optionally count a segment as hit when its own best offset agrees with the global one within ±1 bin.

Add the four cases above as tests. Fix the wiki text.

### m1 – Mixcloud listings are not lazy: paged backfill and `newest_last` (Minor)

`ytclient.py:2135-2185` (`_McMixin`) extends yt-dlp's `MixcloudPlaylistBaseIE._real_extract`, which first
collects all pages into a list.

- **Paged backfill:** in `list_source_paged` the `_PagedGate` can only flush entries after the last page. If the
  backfill is interrupted (pause, app exit, backoff on page 19 of 20), every walked page is dropped and requested
  again on resume, and the cursor never advances. The cost estimate for the headless run assumes progress per page
  (`backfill.py:61-79`).
- **`newest_last` sources:** a Mixcloud playlist with `newest_last` has no head cap. All pages are fetched before
  `_newest_last_handler` can enforce `NEWEST_LAST_MAX`.

Proposal: write a small lazy listing extractor (as for hearthis.at) that pages via `_call_api` and yields per
page. Or at least cap `_call_api` for tail windows at `NEWEST_LAST_MAX`, and for paged backfills at `limit`.

### m2 – Mixcloud search follows `paging.next` blindly (Minor)

`ytclient.py:2120-2121`: the next URL from the API answer is requested as is (any host or scheme). It does go
through the throttle and the proxy, but only `https://api.mixcloud.com/` should be accepted. Otherwise stop.

### m3 – Fixtures are synthetic, not recorded; the hearthis API shapes are unverified (Minor)

`tests/fixtures/platforms/README.md` says the fixtures are "built from the response shapes … made up". Commit
000eee7 says "recorded fixtures". These assumptions are untested against the live API:

- `api-v2.hearthis.at/set/<slug>/` without the user
- `?type=tracks`
- `count`/`page` semantics (a server maximum below 20 would end every listing after the first page, because
  `len(items) < HT_PAGE`)
- the `tracks`/`data` wrapper

CLAUDE.md asks to check the current docs before using these. Before the release, run one real smoke per
platform (search + user listing + set + download) and record one answer each as the fixture.

### m4 – Mixcloud/hearthis 403 blocks never start a backoff (Minor)

`throttle.is_rate_limit_error` only knows 429/bot texts, plus the 403 rule for SoundCloud. Mixcloud sits behind
Cloudflare (yt-dlp calls the GraphQL API with `impersonate=True`). A repeated 403 challenge is not retried, but
it does not pause the platform either: every watchlist source and queued download makes its own request until
the daily limits are reached. Proposal: treat a 403 from `[mixcloud…]` GraphQL/API calls as a block, as
`_SC_BLOCK_PATTERNS` does for SoundCloud, or document the decision in `docs/decisions.md`.

### m5 – Logic in `api.py` (Minor)

`api.py:1886-1893` (re-upload filter in `get_library`) and `api.py:2325-2349` (`get_reuploads` builds and sorts
rows) are core logic. Move them into `fingerprint.py` (e.g. `list_reuploads(db, state)`, `annotate(items)`) so
`api.py` stays thin and both are unit-testable without the Api.

### m6 – Same-platform pre-check and series with fixed length (Minor)

`duplicates.find_duplicate(..., same_platform=True)` uses Jaccard ≥ 0.8 and ±5 s. Weekly shows with long,
mostly identical titles ("… Hardcore Radio Episode 101 (Uptempo Special) …" vs "… 102 …", both 60:00) reach
0.82 from about 10 tokens. With `reupload.precheck` on, every new episode of an `auto_download` source goes to
the inbox. The default is off, so this is not a bug. Mention it in the settings help, or require identical
number tokens for same-platform hits.

### n1 – Fingerprint written after the item was deleted (Nit)

If `process` (`fingerprint.py:544-593`) is decoding when the user deletes the item, `forget` runs first and
`store` then writes print and index rows for an `ignored` item. This is harmless, because candidates are
filtered by `done`, but the rows are dead. Proposal: in `store`, re-check `status='done'` inside the
transaction.

### n2 – Deleting while ffmpeg reads the file (Nit, Windows)

A library pass holds the file open. On Windows a delete, rename or retag of exactly that item fails with "in
use" until the window has been decoded (≤ seconds). Proposal: let `delete_library_item` cancel or skip the
current fingerprint item when it is the same id.

### n3 – `fingerprint.linked_to` is unused (Nit)

`fingerprint.py:515-521`: "linked" is currently only a label. Use the function (e.g. in the player or DJ page)
or remove it.

### n4 – hearthis secret links (Nit)

`platforms._HT_TRACK_RE` only accepts `/<user>/<track>/`. yt-dlp also accepts the third segment of private
share links (`/<user>/<track>/<key>/`). These are refused with "unsupported URL". That is fine, but mention it in
`docs/wiki/Supported-Sources.md`.

## Summary

Fix M1 and M2 (with tests and the wiki text), then this can be released. m1–m4 should go into the same round if
possible. m1 and m4 concern sparing the new platforms, and m3 needs a real smoke per platform anyway.
