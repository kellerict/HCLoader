# Review v0.6.0 – Tracklist search

Range: `git diff 6d0c2e9..HEAD` (5 commits, a72d228 … 245559c). Translation catalogs were only spot-checked.
Reviewer: independent `reviewer` agent; no code changed.

## Verdict: **FREIGEGEBEN**

No Blocker, no Major. The minor findings below can go into a follow-up.

Checked and in order:

- **FTS5 injection:** `_query_tokens` (`app/core/tracklist.py:591`) folds the input to letters/digits only
  (`fold` removes `"`, `*`, `:`, `^`, `(`, `-`, `_` and the rest), max. 12 tokens, each one quoted as `"w"*`, and the MATCH
  string is passed as a bound parameter. I tried `"`, `a" OR "b`, `NEAR(a b)`, `*`, `AND`, `NOT`, `x:y`, `^a`, `-a`
  and `'; drop`: none of them raises an error, and FTS operators only ever end up as quoted literal words.
- **LIKE:** `_like_escape` + `ESCAPE '\'` work. `%`/`_` cannot reach this code anyway (fold removes them).
- **Migration 10:** runs in the existing per-step transaction with a pre-migration backup. The FTS5 probe uses a
  `temp.` table, so nothing persists. Triggers `ai/ad/au` keep `tracks_fts` in sync, also on `ON DELETE CASCADE`
  (SQLite fires triggers for cascade actions). Reusing a rowid is safe because the delete trigger runs first.
- **Index consistency:** delete puts the item into `ignored` (`library._delete_item`), and search, top and status
  filter on `status = 'done'`. A move or retag does not change the tracks, which do not store a path. A re-download
  refreshes the tracklist in `YtClient` (`ytclient.py:1297`, `safe_refresh`, never fatal).
- **Performance / threads:** the pass runs in the maintenance worker (`api.py:2038`). It can be cancelled after
  each item, reports progress every 10 items and uses one short transaction per item. Before it starts, it checks
  that the target folder is reachable, so a dead share is skipped. Shutdown sets `_tl_cancel`.
- **Parser ReDoS:** lines over 200 characters are dropped, and `clean_text` collapses whitespace, so the nested
  `\s*` groups in `_TRAIL_RE` cannot blow up. Fuzz timings (100 adversarial lines each: dashes, brackets, `feat`
  chains, numbers, unterminated timestamps) stayed under 25 ms. A 5000-line «Tracklist:» block took 0.4 s and was
  capped at 300 tracks.
- **XSS:** every untrusted value in `ui/js/views/tracks.js` goes through `esc()`. `mark()` escapes each character
  and only inserts its own `<mark>` tags. Translations that get `{q}` receive `esc(query)`. `data-at` is `+number`,
  `ui.thumb` only allows thumbnails from the CDN whitelist, and `ui.pbadge` is static. Playwright XSS tests exist and pass.
- **Player seek:** `playAt` → `play()` → `get_media(id)` reuses the existing path, which resolves the file by ID.
  The UI never passes a path. External mode only calls `play_external(id)`.
- **Boundaries:** `tracklist.py` makes no network calls and does not import `yt_dlp`. `api.py` only delegates.
  `ytclient.py` remains the only `yt_dlp` importer (plus the existing version checks in binaries/maintenance/main).
  Throttle rules are unaffected.
- **i18n:** new backend keys (`tracklist.*`, `job.tracklists`) and UI keys (`tracks.*`) exist in all catalogs.
  The parity tests pass, and the new German strings use «ss» with no ß.
- **Sidecar 2000→5000:** this matches the YouTube maximum, so the sidecar is still bounded. It only applies to new
  downloads, which `docs/decisions.md` documents. Side effect: if `match_description` is on, retag genre detection now
  sees the whole description (as the download did), which makes retag *more* consistent with the download than before.
- **Bracket fix in `tagging.parse_timestamps`:** a closing `)`/`]` and a trailing `.` are no longer stripped.
  Leading and trailing timestamp brackets are still consumed by the regexes. This is OK.
- Tests: `test_tracklist.py`, `test_api.py`, `test_db.py`, `test_i18n.py`, `test_tracks_ui.py` are green, and `ruff check` is clean.

## Findings

### Blocker
None.

### Major
None.

### Minor

1. **`app/core/tracklist.py:572` / `app/api.py:2006` – `get_tracklist` extracts on demand without a guard.**
   Scenario: a set without a sidecar and with a damaged MP3. Mutagen raises `MutagenError` or `ID3` raises a non-`OSError`
   error, which `extract()` at :448 does not catch, so the raw exception reaches the bridge (generic toast, stack
   trace in the log). With `files_ok=True` on a dead SMB share, the panel call also waits as long as the `stat`
   blocks (js_api thread, not the UI thread).
   Suggestion: in `api.get_tracklist`, wrap the call in `try/except` → `tracklist.search_failed`-style message, and
   pass `files_ok=library.target_reachable(...)`, as the pass does.

2. **`app/core/tracklist.py:543` – `has_fts` only checks whether the table exists, not whether the module is available.**
   Scenario: the DB was created with an FTS5-capable SQLite and is later opened by a Python/SQLite without FTS5 (very
   unlikely on Windows CPython). Then every `INSERT/DELETE ON tracks` fails through the triggers. That includes
   `delete_video` (cascade), which would then also fail. The reverse case is also not covered: a DB migrated without
   FTS5 never gets the index later.
   Suggestion: check `fts5_available()` once at startup. If the table exists but the module is missing, drop the
   triggers and use LIKE. If the module is available but the table is missing, rebuild the index.

3. **`app/core/tracklist.py:614-621` – the two engines behave differently.** FTS matches word prefixes
   (`"hard"*`), LIKE matches substrings anywhere (`%ard%`). The same query gives more hits without FTS5.
   Suggestion: use LIKE with a word prefix (`search LIKE 'w%' OR search LIKE '% w%'`), or document the difference.

4. **`app/core/tracklist.py:674-678` – the «Most played» spelling ignores status.** The spelling query does not
   join `videos`/`status='done'`, so the display form can come from a deleted (`ignored`) set. Tracks of deleted
   sets also stay in `tracks`/`tracks_fts` forever (search filters them out, but they take up space).
   Suggestion: add `JOIN videos … status='done'` to the spelling query, and either clear the tracks in
   `library._delete_item` / `db.mark_removed` or clean them up with a «scope all» pass.

5. **`ui/js/views/tracks.js:252` – after the first pass, the button only offers «all».** Items that become
   `done` outside `YtClient.download` (`worker.py:1003`, «already in archive») are only indexed by a full
   re-read or by opening their panel. This is harmless but slow for large libraries.
   Suggestion: run `scope: 'missing'` automatically when opening the view if `status.scanned < status.total`.

6. **`ui/js/views/tracks.js:53` – the `mark()` guard is weak.** `f !== folded && f.length !== folded.length`
   still lets a different string of the same length through, so highlights can be misplaced. This is only cosmetic:
   the output is escaped character by character. The UI also highlights substrings, while the backend matches word
   prefixes (see 3).

7. **`app/core/ytclient.py:1297` – `safe_refresh` runs before `_record_archive`.** This slightly widens the
   window between `done` and the archive line. It is not critical (the DB status is the truth, and
   `safe_refresh` never raises). For clarity, it could move after `_record_archive`.

8. **`docs/screenshots/*.png` – about 5.8 MB of new PNGs** (7 files at 0.5–1.1 MB) make the repo history bigger.
   Suggestion: use JPG/WebP or smaller crops, as already done for `docs/wiki/images/`.
