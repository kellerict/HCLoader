# Review v0.5.0 – «Festival collector»

Reviewer: `reviewer` (Opus 5.5), independent. Scope: `git diff 7ed51b4..HEAD` (HEAD 68dad08;
translation catalogs only spot-checked). Focus: `app/core/collector.py`, `app/core/timetable.py`,
migration 9 (`app/core/db.py`), the collector methods in `app/api.py`, `ui/js/views/collector.js`.
I did not change any code. `pytest tests/test_collector.py tests/test_collector_ui.py tests/test_api.py`,
the locale parity tests and `ruff check .` all pass locally. I also ran two local
measurements against the code: a timing test of the parser and scoring of sample titles.

## Verdict: ÄNDERUNGEN NÖTIG

No Blocker. One Major: the auto-confirmation accepts any title that *contains* the DJ name.
A row «Angerfist» therefore auto-confirms the b2b set «Angerfist b2b Miss K8 @ Defqon.1 2024».
Because `queue_checklist` queues every checked + confirmed row, this leads straight to wrong
downloads. That is exactly what the «certain» rule is meant to prevent.

The YouTube side is clean:

- Every search goes through `YtClient.search` and therefore through the throttle (backoff,
  `sleep_requests`, `max_searches_per_hour`).
- The collector's own pacing (`interval`, persisted in `collector_last_search`) waits
  *outside* any lock. The pacing wait happens in `run_job` before `client.search`, and the
  metadata lock is only taken inside `_extract`. So the v0.4.0 M1 pitfall does not come back.
- 429 or a bot check stops the job at once (`pending`, with a note).
- A failing row is marked `searched`, so it is never retried in a loop. Three errors in a
  row set the job to `paused`.
- Matching jobs run one at a time in their own worker.
- `LimitReached` waits for the free slot. It cannot hot-loop because `K_LAST_SEARCH` is
  stamped before every attempt.
- The playlist import uses the v0.4.0 paged gate with backfill pacing.

Other checks that pass:

- SQL: fully parameterised. The f-strings only contain fixed column names or names that are
  validated first.
- Migration 9: purely additive, transactional, and runs behind the pre-migration backup.
- XSS: every untrusted value in `collector.js` goes through `esc()`, and links in the
  timetable-file dialog are restricted to `https://`.
- Path traversal: blocked in `timetable.resolve_file`.
- Module boundaries hold: `yt_dlp` is still only in `ytclient.py`, and `core/` has no GUI code.

## Blocker

None.

## Major

### M1 – Auto-confirmation treats «title contains the DJ» as «is this DJ's set» (b2b / multi-artist titles)
`app/core/collector.py:778-783` (`score`), `app/core/collector.py:832-839` (`certain`),
`app/core/collector.py:888-899` (`_apply` stores `confirmed=certain`), `app/core/collector.py:1766ff`
(`queue_rows` queues confirmed rows).

`score()` gives `W_ARTIST` (0.45) whenever the row's artist occurs as whole words in the title.
Nothing checks whether the title also names *further* artists. Measured with the shipped
catalog for Defqon.1 2024:

| row artist | title | result |
|---|---|---|
| Angerfist | `Angerfist b2b Miss K8 @ Defqon.1 2024 \| RED` | 0.90 `[artist, series, year]` → **certain** |
| Angerfist | `Angerfist & Radical Redemption - Defqon.1 2024` | 0.90 → **certain** |
| D-Block & S-te-Fan | `D-Block @ Defqon.1 2024` | 0.75 partial → needs confirmation (correct) |

So the check is asymmetric. A b2b row is protected (partial match), but a solo row silently
takes a b2b/«&»/«vs» set of the same DJ and marks it `confirmed=1`. Festivals routinely book
both a solo set and a b2b or alias set of the same DJ.

Scenario: the solo row comes earlier in `position` and takes the b2b video, already
confirmed. `_taken()` then hides that video from the real b2b row, which ends up «missing»
or with a worse hit. «Queue» downloads the wrong set and tags it with the solo row's
stage/set type (`apply_row_values` → manual festival values). That costs a download,
mislabels the library and breaks the «never twice / right set» promise.

The same blind spot also affects stage and set type. A title that names another stage
(«BLUE») or another set type («Closing Ceremony») for a row with a different one is not
penalised, so it can still reach «certain».

Suggestion: in `score()`, detect a collaboration in the title. Use the row's separators
(`_SPLIT_ARTISTS`: b2b, b3b, vs, &, x, feat, …) next to the matched artist, and count only
the names the row does not list. In that case either apply a penalty or at least drop the
`"artist"` reason in favour of an `"artist:more"` reason that `certain()` rejects. Also make
`certain()` reject a conflicting stage or set type: the title names a known stage or set
type that differs from the row's value. Add tests for the two titles in the table above.

## Minor

### m1 – Quadratic regexes in the timetable parser (long whitespace runs)
`app/core/timetable.py:220` (`_GROUP_RE = \s*[(\[]…`), `:221` (`_LIVE_TAIL = \s+(?:…)$`),
`:253` (`\s*(?:@|\bat\b|[-–—|/])\s*([^@…]+)$`).

All three backtrack quadratically over a long whitespace run that is not followed by the
expected token. Measured with `tt.parse("A" + " " * n + "B")`:

| n (spaces) | time |
|---|---|
| 5 000 | 0.4 s |
| 20 000 | 7.3 s |
| 40 000 | 29 s |

The effect is the same in each of the three regexes (1.7, 1.9 and 3.3 s at 20 000).

`MAX_LINES` limits the number of lines but not their length. The internal whitespace of a
line is never collapsed before `_split_artist`. Neither `Api.parse_timetable` nor the
textarea limit the size of the input. The preview calls `parse_timetable` on every
debounced input (`collector.js` `util.debounce(parse, 220)`), so a bad paste (for example
from a PDF) can keep several bridge threads at 100 % CPU for minutes.

Suggestion: in `parse()`, collapse whitespace per line (`re.sub(r"\s+", " ", line)`) and cap
each line (for example 500 chars). Also cap the text in `Api.parse_timetable` /
`import_timetable` (for example 512 KB, with a translated error). Add a timing test.

### m2 – Weak series aliases count as a full «series» hit and enable auto-confirm
`app/core/collector.py:741` (aliases include `sdef.weak_aliases`), `:789`.

Detection treats weak aliases («Rebirth», «Supremacy», «Loudness», «Intents», «Decibel»,
«MOH») as weak unless a year follows (`festivals.py`). The collector adds the full
`W_SERIES` for them and allows `certain`. Example: a title «Headhunterz – Supremacy (2024
mix)» for a Supremacy 2024 row reaches 0.9.

Suggestion: give a weak alias only a reduced weight, or count it only when the year
follows directly, as the detection does. A weak alias alone must not count as `"series"`
for `certain()`.

### m3 – `confirm_match` can assign a video that another row already holds
`app/core/collector.py:676-689`.

The candidate lists are filtered by `_taken()` only when they are built (`_apply`). If the
user later accepts a candidate that another row of the same edition took meanwhile, two rows
point to the same video. The download is still de-duplicated (`queue_rows` keeps `out`
unique). But `apply_row_values` runs for both rows, the last one wins, and the stage or set
type on the file depends on row order.

Suggestion: re-check `_taken()` in `confirm_match` and refuse with a translated error, or
move the video over.

### m4 – A cancel right after a successful search discards the results
`app/core/collector.py:1663`.

`stop_check()` runs after `client.search` returned and before the hits are scored and stored.
A cancel or app exit at that moment throws away a search that already reached YouTube. The
row is not marked `searched`, so it is searched again later: one wasted request per cancel.

Suggestion: store the hits and set `searched` first, then check for the stop.

### m5 – The matching job holds the yt-dlp update gate for hours
`app/api.py:1649` (`with self._ytdlp_gate.search(): … run_job(...)`).

A job of 300 rows at the default 10/h runs for about 30 h. During that time «Update yt-dlp»
is refused with `GateBusy("search")`. Keeping yt-dlp updatable at the press of a button is a
stated stack goal (CLAUDE.md), and stale yt-dlp versions are the most common cause of
YouTube breakage. The pattern is inherited from the backfill, but the collector makes it
much longer.

Suggestion: enter the gate per search (around `client.search` / `_extract`) instead of for the
whole job. Alternatively, let a requested update set the collector's cancel events; the job
then stays `pending` and is resumed afterwards. In both cases a blocked `_do_matching` should
leave the job `pending` and show a note (today it only toasts).

### m6 – Offline match over all rows runs in the bridge callback thread
`app/api.py:1489ff` (`estimate_checklist_matching` → `collector.estimate` → `match_offline`),
`app/api.py:1520` (`start_checklist_matching`).

`match_offline` scores up to `LIBRARY_SCAN` (300) videos per row. Measured with 1000 rows and
300 edition videos, it takes 5.5 s, and it runs twice when the user clicks Estimate then
Start. CLAUDE.md says long operations never belong in the pywebview callback thread.

Suggestion: run it in the collector worker, or score each video once for all rows.
At minimum, skip the second pass in `start` if `estimate` just ran.

### m7 – The playlist import cannot be cancelled by the user
`app/api.py:1690` (`cancel=self._col_stop`).

Only the app exit stops an import. A large organiser playlist (up to
`watchlist.backfill_max_entries` entries, paced at `backfill_requests_per_hour`) cannot be
stopped from the UI. The import strip has no cancel button either.

Suggestion: add a per-edition import event plus `cancel_checklist_import`, and a cancel button
in the strip.

### m8 – Deleting a user series silently deletes its checklists
`app/core/db.py` migration 9 (`checklists.edition_id … ON DELETE CASCADE`,
`checklist_rows.edition_id … ON DELETE CASCADE`), together with `series.delete_series`
(`DELETE FROM series` → editions cascade).

Deleting a user-defined series removes every checklist of its editions, including the user's
manual work (edited rows, confirmations, rejections), without a word in the delete dialog.

Suggestion: tell the user in the series-delete confirmation how many checklists will be
deleted, or refuse while checklists exist.

### m9 – Timetable files: a UTF-8 BOM breaks them, and the error text is not translated
`app/core/timetable.py:553` (`read_text(encoding="utf-8")`), `:555-580`, shown via
`collector.files_broken` / `collector.file_invalid`.

Windows editors often save JSON with a BOM, and `json.loads` then fails with «unreadable».
The reasons are hard-coded in English («format must be 1», «sets[3]: invalid start») and
appear in the German/Dutch UI. That deviates from the i18n rule, even if it is aimed at
contributors.

Suggestion: read with `encoding="utf-8-sig"`. Give the error reasons keys (code plus
parameters) and translate them in the UI.

### m10 – Searches with more than about 20 results are several YouTube requests but count as one
`app/core/config.py` (`collector_results_per_search` up to 50; the comment says «eine Anfrage pro
Suche»), `app/core/collector.py:1629-1633`.

`ytsearch50:` makes yt-dlp fetch continuation pages back to back, without throttle spacing.
The throttle counts this as one search. The same is already true for `search.results_count`,
but the new setting and its comment suggest that a search is always a single request.

Suggestion: either cap the value at 20, or fix the comment and the estimate
(`requests` = rows × ceil(n/20)).

## Notes (no action required)

- `update_row` resets `searched` for a renamed artist. The running job then picks the row up
  again, so `job_done` can exceed `job_total`. This only affects the display.
- `_library_candidates` filters with `title LIKE '%<longest normalised token>%'`. Artists with
  diacritics («Sóla», «Måhn») miss in the offline match and cost one search. Acceptable.
- `_playlist_rows` assigns a playlist entry to the *first* free timetable row of the same
  artist and ignores the stage. If an artist plays two sets, stage/day can end up swapped
  (both sets still load).
- XSS checked in full: `rowHtml`, `matchHtml`, the candidate and row menus (`ui.menu` escapes
  `label`), the timetable preview, the file list, toasts, modals and `ui.notice` (all callers
  pass `esc(...)`). `stageDot` only uses a colour from a fixed table. Nothing unescaped.
- i18n: the new backend messages use `tr(...)`, the UI uses `t(...)`, and the parity tests are
  green. The German additions contain no «ß».
- Hygiene: there are no binaries, cookies, databases or personal paths in the diff. The three
  new settings are in `config.py`, `config.example.yaml`, `docs/settings-schema.md` and the GUI
  (Settings → Festivals → Collector).

## Nachtrag (integrator, 2026-11-18)

Fixed:

- **M1:** `score()` now flags further artists in the DJ's title segment (`artist:more`), another
  stage (`stage:other`) or set type (`set_type:other`) than the row, an additional year
  (`year:more`) and another series (`series:other`). `certain()` rejects these and the variant
  reasons (`BLOCKS_CERTAIN`). Table-driven tests: `test_conflicting_titles_are_never_certain`,
  `test_exact_titles_stay_certain`, `test_solo_row_does_not_take_the_b2b_set_as_confirmed`.
- **m1:** `timetable.parse` cuts the text to 512 KB, collapses space runs and cuts lines to 500
  characters before any regex. The group/stage regexes no longer start with `\s*`. The test
  covers 40 000 spaces and other long inputs, each under 1 s.
- **m2:** a weak alias counts as `series` only with the edition year right after it. Otherwise
  it counts as `series:weak` (+0.10), which never auto-confirms.
- **m3:** `confirm_match` refuses a video that another row of the edition holds (translated
  `collector.video_taken`).
- **m4:** a search that returned is always stored and its row marked `searched`. A cancel takes
  effect at the top of the loop, and a user cancel keeps the counters.
- **m9 (BOM part):** timetable files are read as `utf-8-sig`.
- **m10:** `collector_results_per_search` is capped at 20 (one request per search), in the
  config, GUI, mock and docs.

Accepted for now (follow-up, no data loss):

- **m5** (update gate held for the whole job): needs a per-search gate and a cancel/resume
  handshake with the updater. Planned together with the backfill, which has the same pattern.
- **m6** (offline match in the bridge thread on estimate/start): about 5 s at the 1000-row
  maximum, typical editions are well under 1 s. Moving it to the collector worker is planned.
- **m7** (playlist import not cancellable from the UI): a run reads 1–3 pages. App exit stops it.
- **m8** (deleting a user series cascades to its checklists): the delete dialog should name the
  number of checklists. This needs UI and texts in 18 languages, so it goes to the next UI pass.
- **m9 (i18n part):** the file error reasons stay English. They are for contributors of
  timetable files, and the surrounding message is translated.
