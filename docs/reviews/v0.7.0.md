# Review v0.7.0 – Loudness, waveform, player memory

Range: `git diff 138c7e7..HEAD` (5 commits, 141d07f … 29d1dc6). I only spot-checked the translation catalogs.
Reviewer: independent `reviewer` agent; no code was changed.
Local run: `pytest tests/test_analysis.py tests/test_playback.py` plus the i18n/parity tests pass, and `ruff check app tests` is clean.

## Verdict: **ÄNDERUNGEN NÖTIG**

No Blocker. There are two Majors: an in-place tag write to the set that is currently playing, and Web Audio
normalisation that has no safeguard against silent output and is on by default.

## Checked and in order

- **ffmpeg call** (`app/core/analysis.py:249-365`): argument list without a shell. The input is the absolute DB path
  after `-i`, so a file name cannot start with `-` and cannot be read as an option. `-nostdin`, `stdin=DEVNULL`,
  `-threads 1`, `CREATE_NO_WINDOW | BELOW_NORMAL_PRIORITY_CLASS` (`nice 10` on other systems). Output goes only to
  a pipe (`s16le`) or `-f null`, so nothing is re-encoded. stderr is drained in its own thread, so a full pipe
  cannot cause a deadlock. A hard 45-minute timeout uses `Timer(proc.kill)`. A watch thread handles cancel
  (also for loudness-only runs), and app shutdown (`AnalysisQueue.stop`, `api.py:309`) kills ffmpeg.
- **Parsing** of the `ebur128` summary: it takes the last "Summary:" block and treats silence or `-inf` as no
  measurement. `framelog=verbose` combined with `-v info` keeps the per-frame lines out of stderr. This is correct.
- **Memory for 2 h or 6 h sets:** at 2 kHz mono there are 10 block maxima per second, so 72k ints for 2 h. Only the
  1600-point reduction is stored (about 6 KB JSON). The UI draws from those 1600 points. This is fine.
- **Waveform cache:** `<app_home>/cache/peaks/<sidecar-stem>.json` is keyed by the id, not the path. A retag or
  move therefore does not invalidate it, which is correct because the audio is unchanged. A re-download is detected
  through `downloaded_at`. Writes are atomic (`tmp` + `os.replace`).
- **ReplayGain tags** (`app/core/tagging.py:554-605`): MP3 replaces only its own TXXX frames (case-insensitive) and
  keeps foreign frames. M4A writes freeform atoms, Opus writes `R128_TRACK_GAIN` (Q7.8, -23 LUFS reference, clamped
  to int16). Reading back R128 adds +5 dB. A retag (`tagging.py` meta keys) does not remove RG frames. The tag write
  runs under `library.FS_LOCK` and reads the path again inside the lock (`analysis.py:525`). A locked or read-only
  file only causes the tag write to be retried, without a new measurement.
- **Gain calculation in the player** (`ui/js/player.js:107-131`): `g = 10^((target-I)/20)`, capped at `1/peak`. With
  no peak it can only attenuate. Without a graph it only attenuates through `audio.volume`. It cannot clip
  (volume ≤ 1, fade ≤ 1). There is no real limiter, but the true-peak cap is enough because the gain is static.
- **Migration 12:** creates new tables only, with `ON DELETE CASCADE` and no change to existing data. The settings
  migration adds the new `loudness` section and new `player` fields with defaults through pydantic, so old
  `config.yaml` files load unchanged. `config.example.yaml` and `COMMENTS` are updated.
- **Configurability:** `player.normalize/target_lufs/resume/waveform` and `loudness.*` are all in the GUI
  (`settings.js`). The pass can be started and cancelled from the GUI.
- **Module boundaries:** `core/` has no UI reference. Nothing new imports `yt_dlp`. No network access, so the throttle
  is not involved. `api.py` only delegates.
- **XSS:** new markup (`library.js` «Continue listening», `player.js` resume bar, `settings.js` analysis box)
  escapes all data with `esc()`. `#pl-norm` uses `textContent`.
- **Resume / sleep timer:** saves every 15 s plus on pause, close, switching sets and hiding the window. Nothing is
  saved while the ask prompt is open. The 30 s margins are checked in the backend. `resume: off` stores nothing.
  The sleep timer fades out through the gain and then sets volume and fade back to 1.
- **Hygiene:** no binaries, cookies or user paths in the diff.

## Major

### M1 – ReplayGain tag write to the set that is currently playing (`app/core/analysis.py:525-546`, `app/api.py:2105`, `app/worker.py` `AnalysisQueue._waveform/_item`)

Scenario: the user plays a newly downloaded set, or an old set that has no waveform yet. `get_waveform` →
`ensure_peaks` → `process(loudness=True)` → `_write_tags` writes the tags into **exactly this file**, while
WebView2 has it open. The same thing happens with `analyse_after_download` when the user presses ▶ right after
the download.

The existing retag path deliberately releases the file first (`HC.player.suspend()/resume()`,
`player.js:536-547`). The analysis path does not.

Effects on Windows:
- Chromium usually opens media files with `FILE_SHARE_READ|WRITE`, so the write succeeds.
- If the ID3 padding is too small (MP3), or for M4A with `moov` in front (yt-dlp `+faststart`), mutagen moves
  the whole audio data in place. On a 2 h set that is hundreds of MB, not atomic, and the playing element is
  reading from offsets that are now wrong. The result is dropouts or a decode error.
- A crash during this move leaves a damaged file.

Suggestion: never write tags to the item that is currently playing. Measure, set `tagged=0`, and leave the tag
write to the next pass or to the point after `player` reports «stopped/other set». The UI already sends
`HC.bridge.emit('player', {id, playing})`, and the backend could mirror that, for example with `api.set_now_playing`.
Alternatively, use the `suspend/resume` mechanism. Mid-term, consider writing the tags to a copy, then
`os.replace` (atomic).

### M2 – Web Audio normalisation without a fallback for silent output (`ui/js/player.js:134-155`)

`createMediaElementSource` cannot be undone. If WebView2 treats the `file:` source as cross-origin, the node
outputs **only zeros**: no error, the element "plays", and the user hears nothing until the app restarts.

The reasoning in `docs/decisions.md` (pywebview sets `--allow-file-access-from-files`) is plausible. I checked
`webview/platforms/edgechromium.py:84-85`, and the flag is set as long as `ALLOW_FILE_URLS` is true. However, the
decision log itself calls it "Offener Punkt: echter Test unter Windows/WebView2", and `normalize` defaults to
`true`. The flag also depends on a pywebview default that a future pywebview version could change.

Suggestion:
1. After building the graph, connect an `AnalyserNode` and check for about 1-2 s while the element is playing
   (`currentTime` advancing) whether `getFloatTimeDomainData` stays at 0. If it does, set `graphBroken = true` and
   tell the user (toast) that normalisation only attenuates. Because the graph cannot be undone, the
   element has to be replaced (`new Audio()` with listeners re-attached, same position).
2. Explicitly set `webview.settings['ALLOW_FILE_URLS'] = True` in `app/main.py`, so it does not depend on the
   default.
3. Run the real Windows test as part of the QA smoke test and record it in `PROGRESS.md`.

## Minor

- **m1 – Short burst at full volume when the graph is built** (`player.js:144-153`, `:124`): the new `GainNode`s
  start at `gain=1`, `audio.volume` is set to 1 in the same tick, and `setTargetAtTime(..., 0.04)` only reaches
  the target after about 100-150 ms. On the first ▶ of a session at volume 0.3 and -8 LUFS material, this gives a
  short loud pop. Suggestion: on a fresh graph, set `rg.gain.value`/`vol.gain.value` directly before
  `connect()`.
- **m2 – ffmpeg holds the file during a retag/move/delete** (`analysis.py:297`): `FS_LOCK` only covers the tag
  write. On Windows, ffmpeg (CRT, without `FILE_SHARE_DELETE`) blocks `rename` and `unlink` of the same file, so
  a retag or delete during the long library pass fails for that one file. Conversely, if the move comes before
  ffmpeg opens the file (between `is_file()` and `Popen`), ffmpeg fails, the error counts as **permanent**
  (`analysed` + `error`), and that set is never analysed again (only by «Analyse all»). Suggestion: treat
  "No such file" on stderr / `not path.is_file()` after the error as `permanent=False`. Optionally, let a retag or
  delete of the current item cancel the analysis first (the cancel event already exists).
- **m3 – A timeout counts as a permanent error** (`analysis.py:320`, `:357-359`): `Timer(proc.kill)` produces a
  returncode ≠ 0 and the same handling as an unreadable file. On a heavily loaded machine (BELOW_NORMAL), a long
  set could be locked out for good. Suggestion: flag the timeout and raise it as `permanent=False`.
- **m4 – ffmpeg is not killed if an exception happens in the read loop** (`analysis.py:337-353`): the `finally`
  closes the pipes but does not call `proc.kill()`. Suggestion: in the `finally`, `if proc.poll() is None:
  proc.kill(); proc.wait(5)`.
- **m5 – Orphaned waveform cache files:** `analysis.forget` is only called by `delete_item` (`api.py:1838`).
  Other paths that end a library item (`db.mark_removed`, maintenance «file missing», re-download with a different
  `downloaded_at` → new file, old one remains) leave `cache/peaks/*.json` behind. These are small, but there is no
  clean-up. Suggestion: in the maintenance clean-up, delete peaks files whose id is not `done` or whose
  `downloaded_at` does not match.
- **m6 – Analysis runs in parallel with the download post-processing:** `AnalysisQueue` is a separate thread, and
  after each download the next download starts at the same time as the analysis (both use ffmpeg). This is softened
  by `-threads 1` and BELOW_NORMAL, and the decision is documented. Even so, it is not «one heavy job at a time».
  Optional: wait while `DownloadQueue` is in the post-processing phase, or only after the queue is empty.
- **m7 – Tag write is not atomic** (`tagging.py:574/595/602`): mutagen writes in place. It is the same as the
  existing `tagging.write`, but now runs automatically over the whole library. See M1 for the copy + `os.replace`
  variant.
- **m8 – Large diffs in locale files that are only formatting:** `ui/js/locales/id.js`, `nl.js`, `ru.js` were fully
  re-indented (about 3500 lines each, `git diff -w` shows only 88). This makes reviews and blame harder. A separate
  `chore:` commit would be better.
- **m9 – i18n detail:** `player.js` `paintNorm` builds `"… dB"` hard-coded. A unit like `unit.lufs` would be
  consistent (a `unit.db` key).
