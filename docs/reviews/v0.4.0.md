# Review v0.4.0 – «Read everything (once)»

Reviewer: `reviewer` (Opus 5.5), independent. Scope: `git diff 8d1a711..HEAD` (commit d371290;
translation catalogs only spot-checked). Focus: `app/core/backfill.py`,
`YtClient.list_source_paged` / `_PagedGate`, `Throttle.backfill_slot`, worker/API/headless
integration, watchlist UI. No code changed. `pytest tests/test_backfill.py
tests/test_backfill_ui.py` and the locale parity tests are green locally.

## Verdict: ÄNDERUNGEN NÖTIG

No Blocker. Three Majors: the backfill holds the metadata lock while it waits for its pacing
slot (search / watchlist checks / download extraction are blocked or fail), a headless
resume can loop forever re-reading the same pages, and a scheduled headless run keeps the
run and watchlist locks for about an hour. The core design is sound: every request goes
through the gate, there is no retry loop, and a 429 stops the backfill at once. The cursor
is idempotent, so a crash can only cause re-reads, never lost or duplicated rows.

## Blocker

None.

## Major

### M1 – Pacing wait runs *inside* the metadata lock (contradicts its own docstring)
`app/core/ytclient.py:1379-1380`, `app/core/throttle.py:447-471`

`_PagedGate.urlopen` takes `th.metadata_lock(...)` and only then calls
`backfill_slot(per_hour)`, which sleeps `3600/per_hour` seconds (default 30 s, up to 360 s at
the allowed minimum of 10/h). The docstring of `backfill_slot` says the wait "runs outside the
throttle lock: searches and downloads are not held up". That is true for the throttle lock,
but the metadata lock (in-process and cross-process) is held the whole time.

Scenarios:
- `watchlist.backfill_requests_per_hour` < 60 (interval > `METADATA_WAIT_S` = 60 s): a GUI
  search or an in-app watchlist check (`_call`, `ytclient.py:664`, timeout 60 s) almost always
  fails with `MetadataBusy` while a backfill runs. A watchlist check counts that as a
  **source error**.
- Default 120/h: every search waits up to 30 s. Every download extraction
  (`ytclient.py:646`, no timeout) waits up to 30 s.
- Headless backfill (cross-process lock): the open GUI is affected the same way for about an
  hour.

Fix: wait for the pacing slot first (`backfill_slot` without the `_request_slot` part,
outside the metadata lock). Then take the metadata lock and run only `request_spacing` /
`_request_slot` (backoff check + `sleep_requests`) before `orig(req)`. Add a test that a
search gets the lock during a backfill pacing wait.

### M2 – Headless resume can livelock: every run re-reads the same pages and makes no progress
`app/core/ytclient.py:869-880` (skip of the first `start` entries), `:1377-1378`
(budget), `app/headless.py:227`

On a resume the gate has to walk the first `start` entries again, and these requests count
against `max_requests` (= `backfill_requests_per_hour`). If
`OVERHEAD + ceil(position / page_size) >= budget`, the run spends its whole budget re-reading
pages it already knows. It raises `RequestBudgetSpent` before it reaches new pages, and the
next scheduled run does exactly the same. This repeats forever.

Example (all values reachable in the GUI): YouTube channel, `backfill_max_entries` 5000,
`backfill_requests_per_hour` 120. Run 1 reaches position ~3570 (119 pages × 30). Every
later run re-reads 120 pages with zero progress, every day, about 1 h each. The same happens
with the default cap of 2000 and any `per_hour` < ~68. In the GUI it ends only if the app
stays open long enough. Repeated app restarts during a long backfill also re-read everything
each time.

This works against principle 1 (YouTube gentleness): a large, permanent number of useless
requests.

Fix: before `run()` in `continue_open`, check whether
`OVERHEAD + ceil(position / page) + 1 > budget`. If so, skip the source in headless mode
without any request, mark it with a note (e.g. "continues in the app"), and do not count it as
progress. Alternatively, guarantee a minimum number of *new* pages per run. Mention the
re-read cost in the estimate dialog when `resume` is true (partly done) and in
`docs/wiki/Scheduled-Checks.md`.

### M3 – Scheduled headless run holds the run and watchlist locks during the ~1 h backfill
`app/headless.py:331-336` (inside `_run`, locks taken at `:130-139`, released only at the end)

`_continue_backfills` runs inside `_run` while the headless process still holds `RUN_LOCK`
and `WATCHLIST_LOCK`. With the defaults (120 requests at 30 s) that is about 60 min. During
this time:
- the GUI download queue cannot start (`run_session` → run lock busy);
- in-app watchlist checks are deferred;
- a yt-dlp update is refused (`api.update_run_active`).

`docs/wiki/Scheduled-Checks.md` mentions "about one hour", but not that the GUI is blocked.

Fix: release the watchlist and run locks before the backfill phase. The `BACKFILL_LOCK`
plus the per-request metadata lock are enough for exclusivity. Or run the backfill phase as
its own step after `_run` returns. Together with M1, the open GUI then stays fully usable.

## Minor

### m1 – Cross-process pause/cancel is ignored; the other process keeps fetching pages
`app/core/backfill.py:246-263`, `:169-178`, `app/api.py` `_stop_backfill`

`pause` / `cancel` only change the DB row and set an in-process `Event`. If the headless
run is reading the source, it does not see the change. All its `only_states=("running",)`
updates silently fail, so the position is no longer persisted, but it keeps requesting pages
until its budget is spent (up to ~1 h). The same applies when `start_backfill` resets a row
that is `running` in another process (`backfill.request` accepts `running`).

Fix: in `on_entries`, treat `update_backfill(...) == False` as a stop signal (raise
`WaitCancelled`). This also covers in-process races. Do not let `request()` touch a
`running` row unless the backfill lock can be taken.

### m2 – Deleting a source does not stop its running backfill
`app/api.py:1091-1094`

`delete_source` does not set `_bf_events[sid]`. The backfill makes at least one more page
request, then fails on the FK in `link_source_video` and logs an error. Fix: set the event
(and drop the row) before deleting.

### m3 – Batch flushed after pause/cancel is ingested but not counted
`app/core/ytclient.py:1374-1376`

`flush()` runs before the cancel check. After a pause, the last batch still goes into the
inbox, but `position`, `added` and `found` are not persisted (state is no longer `running`).
Harmless thanks to dedup, but the counters in the UI are too low. Fix: check the cancel event
before flushing, or accept the batch and persist it regardless of state when the change was
a pause.

### m4 – Redirect path loads up to `limit` entries in one go without intermediate cursor
`app/core/ytclient.py:854-860`

If the first result is `url` / `url_transparent`, `process_ie_result(playlistend=limit)`
fetches all pages before the walk loop runs. If that is interrupted (backoff, budget, exit),
no position is persisted and the whole prefix is lost. Rare for normalized URLs, but
reachable (e.g. SoundCloud short links). Fix: resolve the redirect target with
`process=False` again (one more `extract_info` of `ie["url"]`) and use the lazy path.

### m5 – Backfill can steal new uploads from `auto_download`
`app/core/backfill.py:247-250`

The backfill links every entry it reads to the source (`auto=False`, inbox only). New uploads
after the last check are on the first page. They go to the inbox and are marked "seen", so the
next normal check stops at them and never auto-queues them. Per the spec, results of the
backfill go to the inbox. Still, the user likely expects new uploads of an auto source to be
loaded. Fix: run a normal check of the source right before the backfill starts at position 0,
or document the behaviour.

### m6 – Listing shifts on resume
`app/core/ytclient.py:877`

The cursor is an index. New uploads shift the list forward, which causes re-reads only
(fine). Deleted or privated videos shift it back, so up to that many entries after the
cursor are skipped. Acceptable for a one-time backfill. Document it in
`docs/decisions.md`.

### m7 – SoundCloud client-id discovery is paced like a page request
`app/core/backfill.py:59`, gate

Each script download during client-id discovery waits a full backfill interval (30 s).
`OVERHEAD = 3` underestimates this if several scripts are needed. That is gentle, but the
estimate is off. Possibly exclude `a-v2.sndcdn.com` assets from the pacing (keep the
`sleep_requests` spacing), or raise the overhead.

## Notes (no action required)

- **YouTube gentleness:** every non-loopback request goes through
  `metadata_lock` + `backfill_slot` (backoff check, per-hour pacing persisted in the throttle
  state, `sleep_requests`) + `mark_request`. `sleep_interval_requests=0` is correct because
  the gate spaces requests itself. A 429 or bot check is caught by
  `handle_error` / logger `rate_limit_hit` → backoff; `run()` ends with `pending` and a
  note, with no retry. `continue_open` skips platforms in backoff without a request. One
  backfill at a time (thread `hcloader-backfill` plus the cross-process `BACKFILL_LOCK`).
  Media transfers of the download queue can overlap with a page request. This is the same as
  for watchlist checks and was accepted earlier (metadata lock covers extraction only).
- **Paging semantics:** `process=False` + `lazy_playlist` returns the lazy generator. Entries
  are flushed before the next HTTP request, so the cursor always points behind a complete
  page. No duplicated rows (dedup via `source_videos` / video status), and no skipped pages
  except m6. The cap is checked before `next()`, so there is no extra page request at the cap.
- **Crash safety:** `Ingest` commits per video, then a single `UPDATE` sets the cursor. A
  crash in between only causes re-reads. A stale `running` row is resumed (`OPEN` includes
  `running`) and is protected by `BACKFILL_LOCK`. Migration `_m8_backfill` is additive.
- **Inbox only:** `Ingest(..., auto=False)` never fills `to_queue`; `finish()` gets no
  `enqueue`. Correct.
- **UI / XSS:** source names, notes and errors go through `esc()` (`bfRow`, `bfDone`,
  `ui.modal` title, `ui.toast`). The unescaped `dlg_known` / `dlg_text` contain only catalog
  HTML and numbers. OK.
- **i18n:** new keys exist in `en` / `de`, parity tests are green. Backend messages use `tr()`.
  The YAML comments in `config.py` are German, which is consistent with the existing comments.
- **Boundaries:** `yt_dlp` stays in `ytclient.py`. `backfill.py` is pure core logic.
  `api.py` delegates (thread and event plumbing only). Both settings are in the GUI
  (Settings → Schedule) and in `config.example.yaml`.
